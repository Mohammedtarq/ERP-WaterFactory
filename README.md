# نظام ERP — مصنع المياه (البصرة)

تطبيق سطح مكتب WPF (.NET 9) + SQL Server، عربي بالكامل (RTL)، متعدد المشاريع: قاعدة تحكم مركزية واحدة (`ERP_ControlDB`) + قاعدة مستقلة لكل شركة/مشروع — جاهز لإعادة البيع لشركات أخرى دون أي تعديل.

## التثبيت (للمستخدم النهائي)

**📘 الدليل الكامل: [docs/INSTALL.md](docs/INSTALL.md)**

باختصار: ثبّت SQL Server Express ← شغّل `ERP.Desktop.exe` ← **معالج الإعداد** ينشئ كل شيء (القواعد، الحسابات، العقل المالي، الأدوار، المخازن، المستخدم المدير) ← ادخل.
لا SSMS ولا سكربتات يدوية ولا تعديل ملفات. التحديثات اللاحقة ترقّي قاعدة البيانات تلقائيًا عند فتح المشروع.

**الحزمة الجاهزة:** GitHub ← Actions ← آخر تشغيل ← Artifacts ← `ERP-WaterFactory-win-x64` (تُبنى تلقائيًا بعد نجاح كل الاختبارات)، أو `tools\publish.ps1`.

## للمطوّر

```
ERP.Solution.sln
ERP.Data/            EF Core: الكيانات، السياقات، الخدمات (مبيعات، رواتب، مندوبون، إنتاج...)،
  Setup/             المُثبِّت: سكربتات SQL مضمَّنة + ترقية ذاتية (SchemaVersions) + الإعدادات الأساسية
ERP.Presentation/    منطق كل الشاشات (ViewModels) بلا WPF — مختبر آليًا
ERP.Desktop/         WPF: النوافذ والشاشات XAML، الثيم، المحوّلات، معالج الإعداد
ERP.SeedTool/        التجهيز من سطر الأوامر (نفس المُثبِّت)
Database/            سكربتات SQL (00 → 11)، مضمَّنة في البرنامج
tests/               SQL + تكامل الخدمات + تشغيل الشاشات + فحص ربط XAML
tools/               publish.ps1 / publish.sh، ومولّد شاشات CRUD
```

- **التشغيل من Visual Studio:** افتح `ERP.Solution.sln`، اجعل `ERP.Desktop` مشروع البدء، F5 — يظهر معالج الإعداد أول مرة.
- **الترقية الذاتية:** الملفات 01–08 (المخطط الأساسي) تُنفَّذ مرة واحدة، وقاعدة أُنشئت يدويًا تُكتشف دون إعادة. الملفات 09+ قابلة لإعادة التنفيذ وتُطبَّق كلما تغيّر محتواها. إضافة تعديل للمخطط = ملف `12_...sql` جديد بنفس الأسلوب.
- **شاشة جديدة:** ViewModel في `ERP.Presentation` + UserControl في `ERP.Desktop/Views` + سطر في `Views/ViewMappings.xaml`. شاشات القوائم تُولَّد عبر `python3 tools/gen_crud_views.py`.

| ملف SQL | المحتوى |
|---|---|
| `00` | قاعدة التحكم (المشاريع، المستخدمون العامون، الصلاحيات) |
| `01`–`08` | المخطط الأساسي: الأمان، المالية، المخازن، المشتريات، المبيعات، الموارد البشرية، المندوبون، الإنتاج |
| `09_sales_logic.sql` | منطق المبيعات: التسعير الهرمي، الترحيل الذري، كشف حساب العميل |
| `10_items_barcode_alert.sql` | الباركود وحد التنبيه في الأصناف |
| `11_reps_production.sql` | استبدال مكوّن في الوصفات المخصصة + فهارس الحركات والمحفظة |

## وحدة المبيعات

كل قواعد العمل مطبّقة داخل قاعدة البيانات (`09_sales_logic.sql`)، والتطبيق يستدعيها عبر `ERP.Data/Services/SalesService.cs` — فلا يمكن لأي واجهة تجاوزها.

| في C# (`SalesService`) | في SQL | الغرض |
|---|---|---|
| `CreateInvoiceAsync` | `sp_Sales_CreateInvoice` | فاتورة مسودة؛ يتحقق من العميل، المخزن القابل للبيع، الجهة المستفيدة للمجانية، ويحدد المندوب تلقائيًا من الكاش فان |
| `AddLineAsync` / `DeleteLineAsync` | `sp_Sales_AddInvoiceLine` / `sp_Sales_DeleteInvoiceLine` | السعر يُحسب تلقائيًا إن لم يُمرَّر (سعر القطعة × عدد القطع في وحدة البيع) |
| `PostInvoiceAsync` | `sp_Sales_PostInvoice` | **ترحيل ذري**: مجاميع + ضريبة + مستلزمات تحميل ← خصم مخزون FIFO حسب الصلاحية ← قيد متوازن مرحّل ← محفظة المندوب |
| `DeleteDraftInvoiceAsync` | `sp_Sales_DeleteDraftInvoice` | المسودات فقط؛ المرحّل لا يُحذف |
| `GetSuggestedUnitPriceAsync` | `fn_Sales_BaseUnitPrice` | وكيل ← سعره الخاص؛ عميل فرعي ← سعر وكيله الأب؛ غير ذلك ← سعر البيع العادي |
| `GetInvoiceListAsync` | `vw_SalesInvoiceList` | قائمة الفواتير مع المجاميع والمتبقي |
| `GetCustomerBalancesAsync` / `GetCustomerStatementAsync` | `vw_CustomerBalances` / `vw_CustomerStatement` | رصيد وكشف حساب مستقل لكل عميل (مع رصيد تراكمي) |

الأخطاء تعود كـ `FinanceOperationResult.Fail` برسائل عربية جاهزة للعرض (رصيد غير كافٍ مع الكميات، صلاحية ناقصة، قاعدة ربط ناقصة...) ولا يبقى أي أثر جزئي.

**قواعد الربط المحاسبي المطلوبة** (`AccountMappingRules.TransactionType`): `SalesInvoiceCash`، `SalesInvoiceCredit`، `SalesInvoiceElectronic`، `SalesInvoiceRepCash`، `SalesTax` (الدائن فقط)، `LoadingSuppliesCharge` (الدائن فقط) — تنشئها أداة التزويد تلقائيًا.

**الصلاحيات**: وحدة `Sales` في `RolePermissions` (Add / Edit / Delete / Post) — موظف بلا `CanPost` ينشئ المسودة ولا يرحّلها.

**المبيعات المجانية**: حركة `FreeIssue` (أو `RepFreeSale` من الكاش فان) باسم الجهة المستفيدة، بلا قيد مالي وبلا أثر على رصيد العميل.

**مرتجع زبون** (`CustomerReturnService`، شاشة «المبيعات ← مرتجع زبون»): بضاعة أعادها زبون بعد شرائها.
- **القيمة** بسعر آخر بيع له لنفس العبوة، ولا تتجاوز الكمية ما اشتراه ناقص ما أرجعه سابقًا. **السبب إلزامي**.
- **السليم** يعود للمخزن المختار أو لسيارة المندوب، و**التالف** («منها تالف») لمخزن التالف.
- **التسوية الافتراضية خصم من دينه:** سند «مرتجع» يظهر في كشفه ويدخل توزيع الدفعات، ولا يمس الصندوق. القيد: مدين إيرادات المبيعات / دائن العملاء.
- **رد نقدي من محفظة المندوب** (من السيارة فقط وبرصيد كافٍ): القيد مدين الإيرادات / دائن عهدة المندوبين.
- سند المرتجع لا يُلغى من شاشة السندات، والمرتجع يُطرح من الإيراد والكلفة في الحسابات الختامية.
- مرتجع تطبيق المندوب ينتظر اعتماد صاحب صلاحية «اعتماد طلبات المندوبين»، ويمنع تسوية السيارة حتى يُعتمد أو يُرفض.

## وحدة الموارد البشرية — `ERP.Data/Services/HrService.cs`

كل ثوابت المعادلات في `HrRules` (أعلى الملف) — تعديل أي قاعدة = سطر واحد.

| البند | المعادلة المطبّقة |
|---|---|
| **الحضور** | التأخير = وقت الدخول − بداية الشفت، ويُحسب فقط إذا تجاوز فترة السماح. بلا وقت دخول = غائب (إلا الإجازة المعتمدة) |
| **نقاط الانضباط** | (أيام الحضور × 1 + أيام التأخير × 0.5) ÷ (حاضر + متأخر + غائب) × 100 — الإجازة المعتمدة مستثناة |
| **الحافز الشهري** | المجموع = (الانضباط × وزنه + الأداء × وزنه + المهارات × وزنها) ÷ 100 (الأوزان الافتراضية 40/30/30، مجموعها 100 إلزاميًا)، والمبلغ = شريحة المجموع في مقياس التحويل |
| **حافز المندوب** | Σ (الكمية بالقطعة من فواتيره المرحّلة غير المجانية × حافز القطعة للصنف) |
| **حافز مدير المبيعات** | Σ (الكمية الواقعة في كل شريحة × معدلها) × أيام دوامه الفعلية — الكمية = كل المبيعات المرحّلة غير المجانية للشهر |
| **الراتب الأساسي** | راتب التعيين + كل الزيادات الدائمة السارية حتى نهاية الشهر (من الترقيات والعلاوات، لا يُعدَّل الراتب المخزّن) |
| **البدلات** | المبالغ "لمرة واحدة" السارية داخل الشهر |
| **خصم الغياب** | (الأساسي ÷ 30) × أيام الغياب |
| **الصافي** | الأساسي + البدلات + الحوافز − الخصم |
| **عملتان** | الحوافز تُحسب بالدينار وتُحوَّل لموظفي الدولار بآخر سعر صرف ساري حتى نهاية الشهر؛ التوليد يُرفض إن لم يوجد سعر |
| **الاعتماد** | قيد تلقائي بالدينار (مدين مصروف الرواتب / دائن رواتب مستحقة) عبر قاعدة `PayrollAccrual`، ثم يُقفل الشهر: لا تعديل حضور ولا تقييم ولا إعادة توليد |

## وحدة المندوبين — `ERP.Data/Services/RepsService.cs`

| العملية | ما يحدث |
|---|---|
| **تحميل السيارة** | صادر من المخزن + وارد للكاش فان بنفس التشغيلات (الأقرب انتهاءً أولًا)، في معاملة واحدة، ولا رصيد سالب |
| **البيع من السيارة** | فاتورة المبيعات من مخزن الكاش فان؛ النقد يدخل **المحفظة** تلقائيًا عند الترحيل |
| **مصروف ميداني / تسليم للخزينة** | خروج من المحفظة (لا يتجاوز رصيدها) + قيد: مدين مصروفات ميدانية أو الصندوق / دائن عهدة المندوبين |
| **تحصيل دين عميل** | دخول للمحفظة + سند قبض على العميل (يظهر في كشفه) + قيد: مدين عهدة المندوبين / دائن العملاء |
| **الإرجاع والتالف** | من السيارة للمخزن، أو خصم تالف بسبب "أثناء النقل" |
| **تعارضات المزامنة** | تسوية بملاحظة إلزامية، مع حركة تعيد رصيد السيارة السالب إلى صفر |
| **الأسطول** | تنبيه قبل 30 يومًا من انتهاء إجازة السوق أو السنوية |

## المزامنة السحابية — `ERP.Cloud.Api` + `ERP.SyncAgent`

تربط تطبيق المندوبين بالمعمل عبر خادم سحابي هو صندوق بريد فقط. قاعدة المعمل تبقى الأصل، ولا يُفتح فيها أي منفذ.
- **خدمة المزامنة:** تعمل على جهاز السيرفر. تسحب حركات الهواتف وترحّلها بقواعد `RepAppService` نفسها، ثم تعيد النتائج و«نسخة عمل» كل مندوب: زبائنه وأسعاره ورصيد سيارته.
- **الإعداد:** شاشة «الإعدادات ← المزامنة السحابية». فيها العنوان ومفتاح المعمل والتفعيل واختبار الاتصال و«مزامنة الآن». ويظهر مؤشر الحالة أسفل الشريط الجانبي.
- **التثبيت والنشر وواجهة الهاتف:** `docs/cloud-deployment.md`.
- **تطبيق المندوب (أندرويد):** يُبنى في CI ملف APK. فيه البيع والتحصيل ورصيد السيارة، ويعمل بلا إنترنت، ويُربط برمز QR من «أجهزة التطبيق». الدليل والتجربة عبر واي فاي المعمل: `docs/rep-app.md`.

## وحدة الإنتاج والمختبر — `ERP.Data/Services/ProductionService.cs`

أمر إنتاج (من قائمة المواد + الوصفة المخصصة: المكوّن الخاص **يستبدل** المادة المحددة أو يُضاف) ← **بدء التشغيل** يصرف كل المواد الأولية وينشئ تشغيلة باسم الأمر (كله أو لا شيء) ← **فحص المختبر**: الرقمي ضمن الحدين، الوصفي يطابق المعيار، و**فشل اختبار واحد يرفض الدفعة** ← **التعبئة** (بعد النجاح فقط) تُدخل الكراتين/الشرنك لمخزن المنتج التام ولا تتجاوز كمية الأمر ← **مكتمل** تلقائيًا عند تعبئة الكمية كاملة (أو إغلاق يدوي؛ الفرق هدر).

## الاختبارات

```bash
./tests/run_tests.sh      # يتطلب Docker فقط — يعمل أيضًا تلقائيًا على GitHub Actions
```
1. `Database/00 → 11` على قاعدة نظيفة + `tests/test_sales.sql` (58 فحصًا).
2. بناء كل المشاريع ومنها ERP.Desktop.
3. `tests/ERP.Data.IntegrationTests`: المبيعات، الرواتب بأرقام محسوبة يدويًا، **التثبيت من الصفر والترقية الذاتية وترقية قاعدة يدوية قديمة**، المندوبون، الإنتاج.
4. `tests/ERP.Presentation.Tests`: تشغيل كل الشاشات فعليًا — ومنها **رحلة كاملة من سيرفر فارغ: معالج الإعداد ← الدخول ← إنشاء حساب موظفة ودخولها بصلاحياتها ← الكاش فان والمحفظة ← أمر إنتاج ← المختبر ← التعبئة** — وفحص كل `{Binding}` في كل ملف XAML.
5. `tests/ERP.Desktop.UiTests` (Windows فقط، وظيفة مستقلة في GitHub Actions على LocalDB): **يرسم كل شاشة ونافذة فعليًا عبر WPF**، ثم يثبّت نظامًا ببيانات تجريبية ويفتح كل وحدة وكل تبويب بعد تحميل بياناته. يفشل عند أي خطأ XAML أو مورد مفقود أو خطأ ربط، ويحفظ **صورة لكل شاشة** (Artifacts ← `ERP-WaterFactory-screenshots`).

## ملاحظات تصميمية

- **الأرصدة كسجل حركة (Ledger) لا كرقم مخزَّن**: `StockTransactions` مصدر الحقيقة الوحيد لأي رصيد مخزون، و`RepWalletTransactions` لمحفظة المندوب.
- **مفتاح مؤجل بين 03 و 08** (`ItemBatches.ProductionOrderId`) رُبط عبر `ALTER TABLE` في نهاية 08.
- **الحقول من نوع Enum** نُفِّذت كـ `NVARCHAR` + `CHECK CONSTRAINT`، وتُحوَّل في EF عبر `HasConversion<string>()`.
- **ترقيم المبيعات** بتسلسلات SQL (`SI-2026-000001`، وقيودها `SJ-2026-000001`) — آمن مع المستخدمين المتزامنين.
